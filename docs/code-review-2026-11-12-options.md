| 같은 오행 | 비견 | 겁재 |

코드의 분기 순서와 결과가 전통 십성표와 일치한다. `generatesTo`, `controlsTo`가 올바르게 구현되어 있다는 전제하에 문제가 없다.

### 1-2. 육합 (`branchesCombine`) — ✅ 정확

자축, 인해, 묘술, 진유, 사신, 오미 — 전통 육합 6쌍과 일치한다.

### 1-3. 삼합 (`branchesTriple`) — ✅ 정확

신자진(수국), 해묘미(목국), 인오술(화국), 사유축(금국) — 전통 삼합 4국과 일치한다. `a == b`일 때 `false`를 반환하는 처리도 올바르다.

### 1-4. 역마 (`travellingHorse`) — ✅ 정확

인오술→신, 신자진→인, 사유축→해, 해묘미→사 — 전통 역마표와 일치한다.

### 1-5. 도화 (`peachBlossom`) — ✅ 정확

인오술→묘, 신자진→유, 사유축→오, 해묘미→자 — 전통 도화표와 일치한다.

### 1-6. 배우자성 (`isSpouseStar`) — ✅ 정확

남명=재성(정재·편재), 여명=관성(정관·편관) — 전통 사주학과 일치한다.

### 1-7. 연주 (`yearPillarFor`) — 입춘 기준

> [!WARNING]
> **심각도: 중간** · 위치: `saju_helpers.dart` `yearPillarFor()` 5행

**무엇이 틀렸는가:** 입춘 경계를 **2월 4일 고정**으로 보고 있으며, 조건이 `date.day < 4` — 즉 **2월 3일까지**를 전년으로 처리한다. 이 말은 **2월 4일부터** 새 연주를 쓴다는 뜻이다.

실제 입춘은 매년 **2월 3일 ~ 2월 5일** 사이에서 변동한다 (시각까지 포함하면 2월 3일 밤이나 2월 5일 아침일 수도 있다). 코드 상단 주석에 "간이 만세력 기준"이라고 명시했으므로, **간이 처리로서는 수용 가능**하지만, 2월 3일 또는 2월 5일 생(生)인 사용자에게는 연주가 1년 어긋날 수 있다.

**개선 안:** 최소한 경계를 `date.day < 4`가 아닌 `date.day < 5`(2월 4일까지 전년 처리, 2월 5일부터 신년)로 바꾸거나, 연도별 입춘 일자표를 두면 더 정확하다. 현재 로직은 "2/4 0시부터 새해"이므로 2/4 입춘 이전 시각 출생자도 새해 연주를 받는다.

### 1-8. 월주 (`monthPillarFor`) — 절기 간이표 + 오호둔법

> [!NOTE]
> **심각도: 낮음** · 위치: `saju_helpers.dart` `monthPillarFor()` 15행

`_monthBranch(month, day)`의 구현을 볼 수 없어 세부 절기 경계 정확도는 판정 불가하지만, 오호둔법(五虎遁法)의 공식 `(baseStemIndex + (monthBranchIndex - 2 + 12) % 12) % 10`은 전통 공식과 일치한다.

- 인월(1월 절기) = branchIdx 2를 기준으로 offset 0이 되므로 baseStem이 그대로 인월의 천간이 되는 것은 맞다.

### 1-9. 대운 방향 판정

> [!IMPORTANT]
> **심각도: 높음** · 위치: `decision_options.dart` `scoreChoiceOptions()` 304-305행

```dart
final forward =
    (baby.gender == Gender.boy && isYangStem(saju.year.stem)) ||
    (baby.gender == Gender.girl && !isYangStem(saju.year.stem));
```

**무엇이 틀렸는가:** 전통 대운 방향 규칙:
- 남자(양남) + 양간 년주 → 순행 ✅
- 남자(음남) + 음간 년주 → 역행 ✅
- 여자(양녀) + 양간 년주 → 역행 ✅
- 여자(음녀) + 음간 년주 → 순행 ✅

즉, **남양순·남음역·여양역·여음순**. 코드의 `forward` 조건:
- 남자 + 양간 → `true` (순행) ✅
- 남자 + 음간 → `false` (역행) ✅
- 여자 + 음간 → `true` (순행) ✅
- 여자 + 양간 → `false` (역행) ✅

**결론: ✅ 정확하다.** 재확인 결과 전통 규칙과 일치한다.

### 1-10. 대운 교체 해 판정

> [!WARNING]
> **심각도: 중간** · 위치: `decision_options.dart` `scoreChoiceOptions()` 307-308행

```dart
final age = now.year - birth.year + 1; // 세는나이
if (age >= startAge && (age - startAge) % 10 == 0) {
```

**무엇이 틀렸는가:** `daewoonStartAge`가 어떤 값을 반환하는지에 따라 다르지만, 일반적으로 대운은 **10년 주기**로 교체된다. 이 코드는 `startAge`에서 시작하여 정확히 10의 배수 해만 교체 해로 판정한다. 이 자체는 맞다.

그러나 `age`를 `now.year - birth.year + 1`(세는나이)로 계산하는데, `daewoonStartAge`도 세는나이 기준을 반환해야 일관성이 맞다. 만약 `daewoonStartAge`가 만 나이를 반환한다면 1년 어긋난다. **`daewoonStartAge`의 구현을 볼 수 없어 확인 불가**이지만, 기준 통일 여부를 반드시 확인해야 한다.

## 2. 로직 오류

### 2-1. 점수 합산·클램프

> **심각도: 낮음** · 위치: `decision_options.dart` 332-338행

50점 기준에서 가감하고 `clamp(0, 100)` 처리. 로직 자체는 문제없다.

다만, **A와 B 모두 한 방향으로 점수가 쏠리면 둘 다 50점 이상**이 될 수 있다. 예: 이직에서 모든 요인이 B(이직) 쪽에만 점수를 주면, A는 50점 그대로, B는 80+점이 된다. A가 "무조건 50점 이상"이 되는 것이 의도된 것인지 확인 필요. 현재 구조에서는 A에서 감점하는 경로가 일지 충(이직·이사에서 `_Factor(clashWeight, 0, ...)` 즉 A에 가산)뿐이고, A에서 **감점**하는 `_Factor`는 없으므로, A 점수가 50 미만이 되는 경우는 사실상 없다.

### 2-2. 대운 null 처리

> **심각도: — (문제 없음)**

`stemSources`에서 `if (pillar == null) continue;` 처리(182행), 역마에서 `if (daewoon != null && ...)` 처리(217행). null-safe하다. ✅

### 2-3. 용신 null 처리

> **심각도: — (문제 없음)**

`if (yongsin != null && ...)` 조건(316행). null-safe하다. ✅

### 2-4. 같은 날짜 엣지 케이스

> **심각도: 낮음** · 위치: `decision_options.dart` `scoreTimingOptions()`

`dateA == dateB`이면 두 점수가 같아지고 `_recommendationFor`에서 '비슷함'이 나온다. 동작은 올바르지만, **UX 관점에서** 같은 날짜를 입력하는 것 자체를 막는 것이 좋다 (이건 UI 레이어의 문제).

### 2-5. `_Factor.total`의 용도

> [!WARNING]
> **심각도: 중간** · 위치: `decision_options.dart` 108행, 342행

```dart
int get total => aPoints + bPoints;
```

이것을 정렬 기준으로 사용해 "기여도가 큰 순"으로 뽑는다. 그런데 `_Factor`는 항상 한쪽만 0이 아닌 구조이므로 `total`은 사실상 `max(aPoints, bPoints)`와 같다. 만약 미래에 A와 B 모두에 점수를 주는 Factor가 생기면, `total`이 실제 영향도와 괴리가 생길 수 있다 (A+5, B+5인 Factor는 total=10이지만 결과에 미치는 영향은 0). 현재 코드에서는 문제가 없지만 확장 시 주의.

### 2-6. reasons 표시 로직

> [!WARNING]
> **심각도: 중간** · 위치: `decision_options.dart` 344-346행

```dart
final points = f.aPoints > 0 ? f.aPoints : f.bPoints;
final side = f.aPoints > 0 ? 'A안' : 'B안';
```

`aPoints`와 `bPoints`가 **둘 다 0**인 Factor는 `factors`에 추가되지 않으므로 현재는 문제없다. 그러나 `aPoints`와 `bPoints`가 **둘 다 양수**인 경우가 생기면, `bPoints`가 무시된다. 2-5와 같은 맥락의 잠재적 문제.

## 4. 기타

### 4-1. 이직·이사에서 관성·인성의 방향 해석

> **심각도: 낮음** · 위치: `decision_options.dart` `_stemPoints()` 145-146행

코드에서 관성(편관·정관)이 나오면 **B안(이직/이사) 쪽**에 점수를 주고, 인성(편인·정인)이 나오면 **A안(유지) 쪽**에 점수를 준다.

- 관성 = 직장·변동의 별 → 이동 쪽에 유리하게 보는 것은 합리적.
- 인성 = 안정·보호 → 유지 쪽에 유리하게 보는 것은 합리적.

전통적으로 관성은 "직장·명예"이지 "이직"은 아니지만, 변동을 의미하는 것은 맞으므로 해석의 범위 안에 있다. ✅

### 4-2. 결혼에서 일지 충 해석

> **심각도: 낮음** · 위치: `decision_options.dart` 231-236행

일지 충 시 결혼 카테고리에서 **B안(새 인연) 쪽**에 점수를 준다. 전통 사주에서 일지 충은 배우자궁이 흔들린다는 의미인데, 이를 "지금 인연을 신중히"로 해석하고 B(새 인연)에 가산하는 것은 논란의 여지가 있다. 일지 충은 모든 인연 관계가 불안정하다는 의미이지, 새 인연이 유리하다는 의미는 아닐 수 있다. 그러나 앱의 A/B 이분법 구조 안에서 어느 쪽에 넣어야 하는지의 문제이므로, **해석상 선택**으로 볼 수 있다.

### 4-3. `branchesClash` 함수 누락

> **심각도: — (확인 불가)**

`branchesClash`가 `saju_helpers.dart`에 없다. `saju.dart`에 있는 것으로 보이며, import 경로(`import 'saju.dart'`)로 가져온다. 육충 6쌍(자오, 축미, 인신, 묘유, 진술, 사해)이 올바르게 구현되어 있는지는 `saju.dart`를 봐야 한다.

| 5 | 낮음 | **의도된 설계로 확인** | 50점은 중립 기준이고 요인은 각 선택지의 지지도를 더하는 방식이라 점수는 50점에서 위로만 올라간다. 우열은 점수 차이(10점 기준)로 가린다. decision_options.dart 합산 부분에 주석으로 명시했다. 코드 변경 없음. |
| 6 | 낮음 | **해석상 선택으로 수용** | 결혼 시 일지 충을 B안(새 인연)에 가산하는 것은 "지금 인연은 신중히"라는 주의 신호를 이분법 안에서 표현한 것이다. 이유 문구(`지금 인연은 신중히 살펴보세요`)가 새 인연을 보증하지 않음을 분명히 한다. 코드 변경 없음. |

정확하다고 확인된 부분: 십성·육합·삼합·역마·도화·배우자성·대운 방향 — 전통 사주학과 일치. `branchesClash`는 기존 decision.dart의 함수로, 별도 테스트(육충)가 있다.
